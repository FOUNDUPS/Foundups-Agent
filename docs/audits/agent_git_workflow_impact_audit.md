## 1. Current Workflow Truth

**Branching model:** Short-lived feature branches with prefix conventions (`bl/`, `bn/`, `feat/`, `fix/`, `docs/`). 49 branches exist; merged branches have not been auto-deleted (until today's toggle). Branches are created per-PR, not long-lived.

**Merge model:** Architect-called merges. Foundup (single Member account) opens PRs and merges them. All 3 merge types enabled (merge commit, squash, rebase). Most recent 10+ merged PRs show single-commit merges into main. No evidence of auto-merge usage.

**PR review model:** PRs are required via ruleset ("rules" ruleset, active, targeting default branch). However, **required approvals = 0**. PRs have "No reviews" and "1 participant" consistently. This is a structural gate (forces branch->PR->merge), not a review gate. The PR author merges their own PR.

**CI/check behavior:** Single workflow `ci.yml` with 3 jobs: `test` (pytest on simulator + FAM tests), `lint` (ruff with `--exit-zero`, meaning lint never fails the build), `security` (git grep for secret patterns + .env tracking check). CI runs on push to main and on pull_request to main. **CI is advisory only** - "Require status checks to pass" is NOT enabled in either ruleset. Merges can proceed regardless of CI outcome. The lint job literally cannot fail (`--exit-zero`).

**Agent tooling:** PRs are generated by Claude Code (evidenced by "Generated with Claude Code" footer). CLAUDE.md contains extensive 0102 agent operational instructions. `.claude/` and `.agent/` directories exist. Agents operate through PR flow, not direct-to-main pushes (enforced by "Require a pull request before merging" rule).

**Task-authoritative surfaces:** PRs only. Issues are barely used (1 open, 0 closed out of 308 merged PRs). Project board exists but is untitled and private. No milestones. Labels are default GitHub set only.

**Branch protection state (actual):**
- Ruleset "Main Branch Protection": Active but **0 rules checked** - empty shell
- Ruleset "rules": Active, 2 rules: Restrict deletions, Require PR before merging (0 approvals required, no status checks required)
- No bypass list on either ruleset
- "Require status checks to pass" = OFF
- "Block force pushes" = unchecked

**Community files present:** README.md, CONTRIBUTING.md, LICENSE
**Community files missing:** CODE_OF_CONDUCT.md, SECURITY.md, Issue templates, PR template, CODEOWNERS, FUNDING.yml

## 5. Hold / Not Ready

- **Auto-merge** - No trusted required checks exist. Lint uses `--exit-zero`. Test coverage is partial. Architect-called merge model is intentional.
- **Require status checks to pass** - CI signal quality is not yet reliable enough. The `lint` job cannot fail. The `test` job covers only simulator and FAM modules. Making these required would either (a) block merges on irrelevant failures or (b) provide false confidence.
- **Required approvals > 0** - Single-contributor workflow. Agents create and merge their own PRs. Adding review requirements would halt all agent work.
- **Block force pushes** - Low urgency since PR-required rule exists. Audit whether agents ever force-push first.
- **Require up-to-date branches** - Would serialize all PR merges. With 6 concurrent open PRs and high merge velocity (~10 PRs/day), this creates a severe bottleneck.
- **Dependabot version updates** - High noise for unclear value at this stage.
- **Secret scanning as merge gate** - Need baseline alert data first.

---

## 6. Preconditions for Tighter Governance

Before enabling **auto-merge**, these must be true:
1. `lint` job must be able to fail (remove `--exit-zero` from ruff)
2. `test` job must cover modules that PRs actually touch (not just simulator + FAM)
3. At least one status check must be required and trusted
4. False positive rate for all checks must be < 5%

Before enabling **required status checks**:
1. Audit which CI jobs are stable enough to gate on (currently: `security` job is the most reliable; `test` is partial; `lint` is disabled via `--exit-zero`)
2. Consider splitting CI into "must-pass" and "advisory" jobs
3. Run 2-week observation of check pass rates across all PRs

Before enabling **required reviews**:
1. Either a second human reviewer must be available, OR
2. A bot reviewer (e.g., GitHub Copilot code review, or a CI-based review bot) must be configured
3. The Foundup account must not be able to self-approve

Before tightening **branch protection**:
1. Verify no agent workflow depends on force-pushing to main
2. Verify no agent workflow depends on merged remote branches remaining available (auto-delete is now on - monitor for breakage)
3. Document the intended merge cadence in CONTRIBUTING.md

## Biggest Workflow Risk If Settings Are Tightened Too Early

**Requiring status checks to pass when lint uses `--exit-zero` and test coverage is partial.** This creates a false safety signal - merges appear gated but the gate doesn't catch real problems. Worse: if `--exit-zero` is removed without broadening test coverage first, legitimate PRs touching modules outside simulator/FAM would be blocked by lint failures on existing code, halting the entire agent pipeline.
