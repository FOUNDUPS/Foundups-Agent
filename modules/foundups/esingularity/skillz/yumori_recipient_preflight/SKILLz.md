# YUMORI Recipient Preflight

## Purpose

Prevent misaddressed, duplicate, stale-route, and consent-violating correspondence before Gmail send.

Recipient correctness is a transaction-time authorization decision. A recipient that was valid in an older thread or Contacts row is not automatically valid for the next send.

This skill is designed as the YUMORI production reference for a reusable Red Dog `recipient_preflight` guard.

## Trigger

Run before every external send or recipient-finalized draft generated by a YUMORI/Red Dog correspondence workflow, including:

- new messages;
- replies and follow-ups;
- delivery repairs;
- corrections;
- multi-recipient campaign or government correspondence;
- any AUTO send.

HIGH/CRITICAL messages must never bypass this skill.

## Source precedence

Resolve each intended destination from the freshest authoritative evidence in this order:

1. explicit recent recipient instruction in the complete provider thread or authoritative provider record;
2. binding Correspondence Routing state;
3. canonical Contacts record;
4. established prior thread route;
5. current authoritative public organization directory only when no verified route exists.

A newer explicit instruction overrides older Contacts/history.

Search snippets, summaries, model memory, copied prose, autocomplete and similar-looking addresses are not exact-address evidence.

If exact text is ambiguous or conflicting, read the complete provider message and inspect raw MIME/header evidence.

## Address normalization

Normalize only:

- address case;
- surrounding whitespace;
- display-name syntax.

Do not silently alter:

- hyphens;
- dots;
- plus tags;
- subdomains;
- local-part spelling;
- domain spelling.

A one-character or punctuation difference is `NEAR_MATCH`, not a correction.

## Two-pass gate

### Pass A — identity and policy

For every intended person or organization:

- resolve Contact ID when one exists;
- classify person route vs organization route;
- load current Correspondence Routing;
- enforce `DO_NOT_ADDRESS_OR_CC`, `PERSONAL_ROUTE_CLOSED`, BCC-only, organization-only and related restrictions;
- determine the authoritative route source and its evidence timestamp.

Output per intended identity:

```text
identity
contact_id
route_type
policy
authoritative_source
source_timestamp
authoritative_address
```

### Pass B — exact transaction

Construct the exact final `To`, `CC` and `BCC` set that will be submitted to Gmail.

Independently recompute recipients from Pass-A evidence. Do not accept the response composer's recipient list as authoritative.

For each final address assert:

- exact normalized equality with the authoritative route;
- route is not closed or restricted;
- intended role is correct: TO / CC / BCC;
- the address belongs to the intended identity;
- required intended recipients are covered;
- no unintended recipient was added;
- Sent does not already contain the same newly-authored ask for that recipient/thread unless an explicit resend reason exists.

If any recipient is `UNKNOWN`, `CONFLICTING`, `STALE`, `NEAR_MATCH`, `CLOSED`, or lacks authoritative evidence:

```text
decision = BLOCK
mode = DRAFT or ESCALATE
```

Do not send.

## Recipient state

Track state per recipient, not only per Gmail message:

```text
VERIFIED_ROUTE
  -> VERIFIED_SENT
      -> VERIFIED_BOUNCED
      -> SUBSTANTIVE_REPLY
      -> DELIVERY_UNKNOWN
```

Absence of a bounce does not prove delivery.

A multi-recipient message may be provider-successful while one intended recipient is missing or wrong.

## Preflight receipt

Every HIGH/CRITICAL send emits an internal receipt before execution:

```yaml
message_intent:
thread_id:
importance:
recipients:
  - identity:
    contact_id:
    role: TO|CC|BCC
    route_type: PERSON|ORGANIZATION
    authoritative_source:
    policy:
    exact_match: true|false
    duplicate_coverage: clear|blocked
decision: SEND|BLOCK
```

Private addresses and BCC data stay internal and never enter public Git or Moshpit.

## Send boundary

The Gmail send adapter must accept recipients only from a successful preflight receipt.

Do not allow caller-supplied arbitrary recipients to bypass the validator.

This is a fail-closed boundary: missing validator state means no send.

## Post-send verification

Immediately after send:

1. read the exact Gmail Sent message;
2. compare actual To/CC/BCC with the preflight receipt;
3. verify message_id and thread_id;
4. persist per-recipient `VERIFIED_SENT`;
5. treat any recipient mismatch as a send-integrity incident;
6. reconcile Gmail -> Email Log -> Contacts -> Action Queue;
7. write Moshpit only when campaign-significant.

## Delivery repair

For bounce or rejection:

1. inspect actual DSN/SMTP evidence;
2. isolate the failed recipient;
3. rerun both preflight passes;
4. repair only the missing recipient;
5. never resend the full original list by default;
6. if corrected routing is uncertain, DRAFT/ESCALATE.

## Tests

Minimum contract tests:

- stale Contacts route vs newer explicit recipient instruction;
- closed personal route vs active organization route;
- one-character or hyphen near-match;
- display-name parsing without changing mailbox text;
- stale autocomplete address;
- mixed valid/invalid multi-recipient message;
- missing intended recipient;
- unintended CC/BCC recipient;
- duplicate resend to already-covered recipient;
- recipient-specific bounce repair;
- reply-thread recipient drift;
- preflight receipt vs Sent read-back mismatch;
- absence of authoritative route evidence;
- source conflict requiring raw provider evidence.

## Design basis

The guard combines three established patterns:

- pre-send recipient warnings such as enterprise mail MailTips;
- allowlist-style exact input validation;
- deny-by-default authorization validated on every transaction.

The operating rule is simple: resolve identity first, authorize route second, compare exact recipients third, send only after all three agree.
