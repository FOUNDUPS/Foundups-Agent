## 1. ROC Definition

**ROC = Return on Compute** (Trademark of EDUIT, Inc.)

```
ROC = (V_generated - C_compute) / C_compute
```

Where:
- `V_generated` = Value generated by compute (revenue from completed tasks)
- `C_compute` = Cost of compute (infrastructure expenditure)

**Equivalent formulations:**
- `ROC = compute_margin / compute_spend`
- `ROC = (Marginal Revenue - Marginal Cost) / Marginal Cost`
- `ROC = Value Added / Input Cost`

## 2. Academic References

### 2.1 FinOps Unit Economics
**Source**: [FinOps Framework - Unit Economics](https://www.finops.org/framework/capabilities/unit-economics/)

> "Cloud Unit Economics achieves goals by leveraging measurement of marginal cost (unit cost metrics) and marginal revenue (unit revenue metrics). By calculating the difference between marginal cost and marginal revenue, practitioners can determine where cloud operations break even and begin to generate profit."

**Key insight**: ROC IS the FinOps unit economics formula applied to compute.

### 2.2 Bureau of Labor Statistics - Productivity Measurement
**Source**: [BLS - How is productivity measured?](https://www.bls.gov/k12/productivity-101/content/how-is-productivity-measured/output.htm)

> "Value added is the difference between gross output and intermediate inputs and represents the value of labor and capital used in producing gross output."

**Mapping**:
- Gross Output = V_generated (revenue from compute tasks)
- Intermediate Inputs = C_compute (infrastructure cost)
- Value Added = V_generated - C_compute = numerator of ROC

### 2.3 Total Factor Productivity (TFP)
**Source**: [Wikipedia - Total Factor Productivity](https://en.wikipedia.org/wiki/Total_factor_productivity)

> "TFP is usually measured as the ratio of aggregate output to aggregate inputs."

**Formula**: `Y = A × K^α × L^β`
- Y = Output
- A = TFP (efficiency multiplier)
- K = Capital
- L = Labor

**ROC as TFP**: In compute economics, ROC measures how efficiently compute (K) generates value (Y).

### 2.4 arxiv:2510.26136 - Beyond Benchmarks: Economics of AI Inference
**Source**: [arxiv:2510.26136](https://arxiv.org/html/2510.26136v1)

**Key formulas from paper**:
```
Production Function: Intelligence = f(Cost, Model)
GPU Hourly Cost = Depreciation + Power + Maintenance
  - Depreciation = P / (Y × 8760 × u)
  - Power = kW × PUE × E
  - Maintenance = (P × m) / 8760
```

**Variables**:
- P = GPU purchase price
- Y = depreciation period (3 years)
- u = utilization rate (0-1)
- kW = power consumption
- PUE = data center efficiency (1.3-1.5)
- E = electricity price
- m = maintenance rate (3%)

**Our C_compute** embeds these via cloud pricing (AWS/GCP include depreciation, power, maintenance in their rates).

### 2.5 Inference Economics Metrics
**Sources**:

## 4. ROI vs ROC Dialectic

### 4.1 Traditional ROI
```
ROI = (Revenue - Investment) / Investment
```
- Measures CAPITAL efficiency
- Time horizon: Quarters/Years
- Includes: NPV, IRR, Payback Period

### 4.2 pAVS ROC
```
ROC = (V_generated - C_compute) / C_compute
```
- Measures COMPUTE efficiency
- Time horizon: Ticks/Epochs
- Includes: Task completion, Agent productivity

### 4.3 Synthesis
**ROC IS the pAVS-native ROI.**

| Dimension | ROI (Capital) | ROC (Compute) |
|-----------|---------------|---------------|
| Scarce resource | Money | Compute cycles |
| Value creation | Labor + Capital | Agents + Compute |
| Productivity metric | Revenue/Investment | Value/Compute |

**Litepaper insight** (foundups.com):
> "decision metric shifts from ROI-first capital allocation to ROC-first compute allocation"

## 5. Economic Evolution: From UBI to UCA to ROC

In a compute-native post-money economy, traditional capital-centric distribution and evaluation frameworks fail. This section defines the formal evolution from legacy economic concepts to compute-first structures, bridging economic participation, distribution mechanics, and productivity measurement.

### 5.1 The Transition Paradigm
The transition is defined by two primary shifts:
1. **Capital Efficiency to Compute Productivity**: `ROI -> ROC`
2. **Fiat Redistribution to Resource Allotment**: `UBI -> UCA`

Legacy Universal Basic Income (UBI) functions as a consumption-enabling transfer payment denominated in depreciating fiat currency. In contrast, the Universal Compute Account (UCA) serves as a production-enabling allotment of system compute resources. UCA ensures every participant receives a direct claim on the network's productive capacity, rather than a passive financial voucher.

### 5.2 Notation and Internal Flows
Economic participation is modeled via the UCA container, which transitions through two notation states depending on system maturation.

**Bridge Era (hybrid / external backing)** -- the translation bridge to legacy structures:

```
UCA = UBA + UBR + UBD
```

Where UBA = Universal Basic Allocation, UBR = Universal Basic Reserve, and UBD = Universal Basic Dividend (drip).

**Native Compute Era (compute-native / decoupled)** -- internal economic flows inside the account:

```
UCA = ca + cr + cd

ca = Compute Award       (initial grant / credentialed allocation of compute issued to participants)
cr = Compute Reward      (incentive distributions emitted for verified task completion)
cd = Compute Dividend    (recurring yield distributed to stakeholders from collective compute output)
```

**Casing convention**: Uppercase `UCA` denotes the Universal Compute Account (the macro account / container / identity). Lowercase `ca` / `cr` / `cd` denote internal economic flows inside the account.

### 5.3 Economic Concept Mapping

| Attribute | Legacy Capital Economy | Compute-Native Bridge | Compute-Native Post-Money |
| :--- | :--- | :--- | :--- |
| **Productivity Metric** | ROI (Return on Investment) | Dual ROI/ROC Gate | ROC (Return on Compute) |
| **Participation Metric** | UBI (Universal Basic Income) | UCA (`UBA + UBR + UBD`) | UCA (`ca + cr + cd`) |
| **Growth / Direction** | CAGR (Compounding Growth) | CABR (Benefit Rate) | CABR (Benefit Rate) |
| **Primary Resource** | Fiat Currency / Capital | BTC Backing + Compute | Pure Compute Cycles |
| **Asset State** | Passive Accumulation | Staked/Locked BTC | Circulating Compute / Decay |

### 5.4 ROC as the Bridge to Productivity
While UCA dictates the **distribution** of raw productive potential (inputs) and CABR dictates the **direction** of benefit (utility), ROC measures the **efficiency** of the conversion:

```
ROC = (V_generated - C_compute) / C_compute
```

Thus, UCA provides the participation fuel, CABR provides the value boundary, and ROC validates that the allocated compute operates sustainably.

## 6. Risk-Adjusted ROC (Sharpe-ROC)

### 6.1 Sharpe Ratio Foundation
**Source**: [Wikipedia - Sharpe Ratio](https://en.wikipedia.org/wiki/Sharpe_ratio)

```
Sharpe = (Return - Risk-free) / σ(Return)
```

### 6.2 Proposed Sharpe-ROC
```
Sharpe-ROC = (ROC - baseline_ROC) / σ(ROC)
```

Where:
- `ROC` = actual return on compute
- `baseline_ROC` = minimum acceptable (e.g., 0% = break-even)
- `σ(ROC)` = standard deviation across tasks/epochs

## 8. Quality Adjustment

### 8.1 Implicit Quality Gate (Task Completion)
ROC is already quality-adjusted because:
1. Only COMPLETED tasks generate `V_generated`
2. Failed tasks = no revenue = no V contribution
3. Users only pay (spend UPs) for successful output

### 8.2 Explicit Quality Gate (CABR 3V)
CABR provides the explicit quality gate BEFORE ROC is calculated:

```
Task submitted → CABR 3V evaluation → PoB validation → Payment
                                                         ↓
                                            V_generated (ROC input)
```

**Formula relationship:**
```python
# CABR determines IF task gets paid (quality gate)
if cabr_score >= 0.618:  # CABR_THRESHOLD
    pob_validated = True
    v_generated += task_payment  # Feeds ROC

# ROC measures efficiency of CABR-approved work
roc = (v_generated - c_compute) / c_compute
```

### 8.3 Why NOT to Add CABR Multiplier to ROC
**Risk**: Double-counting since CABR already gates what enters V_generated.

If we did `ROC_quality = (V_generated × cabr_score - C_compute) / C_compute`:
- Tasks with cabr_score < 0.618 are ALREADY rejected (no V contribution)
- Multiplying again would penalize approved work unnecessarily
- Keep gates separate: CABR = quality, ROC = efficiency

## 10. Implementation Reference

### 10.1 Current Implementation
**File**: `modules/foundups/simulator/economics/unified_sustainability.py`

```python
@property
def return_on_compute_ratio(self) -> float:
    """RoC = (V_generated - C_compute) / C_compute = margin / spend."""
    if self.compute_spend_usd <= 0:
        return 0.0
    return self.compute_margin_usd / self.compute_spend_usd
```

### 10.2 Sustainability Gates
```python
# ROC-FIRST: Primary gate (compute productivity)
is_compute_positive = roc_ratio > 0  # PRIMARY GATE

# ROI-PATH: Secondary gate (traditional breakeven)
is_roi_sustainable = margin >= 0  # SECONDARY GATE

# Combined: Both gates must pass
is_sustainable = is_compute_positive and is_roi_sustainable
```
